## 1. C4 — 락온 LoS 통일

### 문제 — 같은 컴포넌트 안에서 두 판정이 다른 트레이스를 썼다

```
획득  FindBestTarget      LineTraceSingleByChannel(ECC_Visibility)
유지  IsTargetStillValid  LineTraceSingleByObjectType(WorldStatic + WorldDynamic)
```

"무엇이 시야를 막는가"의 정의가 달랐다. 갈리는 액터가 레벨에 있으면 **락온이 걸리자마자 풀린다**(또는 반대).

### 통일 방향은 코드가 이미 정해놨다

`AT_MeleeTrace.cpp:89~93` 에 판단 근거가 주석으로 있다.

> Querying the WorldStatic OBJECT type (not Visibility channel) means pawns never occlude

`ECC_Visibility` 는 **Pawn 이 무시하므로 적이 적을 가려주지 못한다.** ObjectType 쪽이 이 프로젝트의 기존 선택이다.

### 결과

```cpp
// LockOnComponent.h (신규 private)
bool HasLineOfSightTo(const AActor* Target) const;
```

두 호출부가 이 한 줄로 바뀌었다. 덤으로 `LosHit.GetActor() != Candidate` 예외 검사가 사라졌다 — 폰을 아예 안 물으니 필요가 없다. `Params.AddIgnoredActor(Target)` 로 대상 자신도 명시 제외.

## 2. C5 — `PostGameplayEffectExecute` 4분해

데미지가 들어오는 **유일한 관문**이 116줄이었다. 새 규칙이 전부 여기 붙으므로(Shield 도 08-18 에 가운데 끼워넣은 것) 방치하면 "패링 고치다 실드가 깨지는" 함수가 된다.

```
IsFrontalAttack       전방판정 + 부호각
TryInterceptByParry   퍼펙트 | 적 방어형 — 삼켰으면 true 반환
ApplyMitigation       Defense 차감 + Shield 흡수 -> 체력 몫 반환
SendHitReact          히트리액션 신호
```

본문이 순서만 보여준다.

```cpp
if (TryInterceptByParry(...)) { return; }
const float ToHealth = ApplyMitigation(ASC, FinalDamage);
const bool bLethal = ...;
if (!bLethal) { SendHitReact(Data, ASC, bBlockedHit); }
ASC->SetNumericAttributeBase(Health, ...);   // 마지막 유지
```

### ⚠️ Health 차감은 일부러 안 뺐다

`:143` 주석대로 **Health 0 도달 시 `HandleDeath` 가 이 스택 안에서 완료**된다. 헬퍼로 빼면 그 아래에 코드를 놓을 수 있게 돼서, 지키려던 제약이 오히려 흐려진다. B2 에서 배운 것과 같은 이야기 — **어트리뷰트에 쓰면 그 줄에서 남의 코드가 돈다.**

## 3. C3 — 빈 상속 층 제거

`UGA_PlayerOneShotAttack` 은 **멤버 0 · 함수 0** 이었다. `.cpp` 는 include 한 줄.

```
전   UGA_PlayerMeleeAttackBase -> UGA_PlayerOneShotAttack -> 자식
후   UGA_PlayerMeleeAttackBase -> 자식
```

### 자식이 둘이 아니라 셋이었다

```
UGA_SprintAttack · UGA_CounterThrust · UGA_PlayerAirAttackBase
```

`PROJECT_OVERVIEW.md` 의 상속 트리 그림은 `AirAttackBase` 를 `PlayerMeleeAttackBase` 직속으로 그려놨는데 **실제로는 OneShot 밑이었다.**

### BP 리페어런팅은 필요 없었다

에셋 레지스트리 전수 조회 — `GA_PlayerOneShotAttack` 을 부모로 삼는 BP **0개**. 그동안 "BP 작업 동반"으로 미뤄뒀던 건 확인 안 한 추측이었다.

`Super::` 호출도 영향 없다. 빈 층은 override 를 안 하므로 **원래도 `PlayerMeleeAttackBase` 로 떨어지고 있었다.**

## 4. ★ 부수 수확 — 달리기 공격이 죽어 있었다

C3 검증 중 BP 부모를 전수 조회하다 발견.

```
GA_SprintAttack (BP)   부모 = UGA_PlayerMeleeAttackBase   AbilityTags = []
GA_CounterThrust (BP)  부모 = UGA_CounterThrust           AbilityTags = [CounterThrust]
```

**BP 가 `UGA_SprintAttack` 을 건너뛰어 태그를 못 받고 있었다.** 태그는 C++ 생성자가 준다.

```cpp
// GA_SprintAttack.cpp:10
AbilityTags.AddTag(GameplayTags::Ability_Player_SprintAttack);
```

그런데 발동은 태그로만 한다.

```cpp
// KDPlayerAbilityInputComponent.cpp:195
if (ActivateByTag(ASC, GameplayTags::Ability_Player_SprintAttack)) return;
```

→ **대상을 못 찾고 조용히 실패.** 에러도 로그도 없다. 게다가 `:78`·`:82` 의 캔슬 목록에도 그 태그가 들어 있어 이동 캔슬·공격 캔슬 판정에서도 안 잡혔다.

**조치** — BP 부모를 `UGA_SprintAttack` 으로 리페어런팅. 태그가 자동으로 들어오고 `AttackMontage`(`AM_SB_Run_Attack_01`) 도 유지됐다. PIE 에서 달리기 공격 정상 확인.

⚠️ **언제부터였는지는 미상.** `.uasset` 이 바이너리라 부모 변경 시점을 이력에서 특정할 수 없다.

📌 교훈 — **BP 가 C++ 중간 클래스를 건너뛰면 그 클래스가 주는 것만 조용히 빠진다.** 나머지 기능은 다 있어서 겉보기엔 멀쩡하다. `[[reference_silent_gas_defects]]` 계열.
