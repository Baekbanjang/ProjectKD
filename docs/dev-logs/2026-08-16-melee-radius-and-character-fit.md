# 2026-08-16 — 근접 판정 반경 측정 + SB 캐릭터 정합

`ANS_MeleeTrace` 28개 창을 전수 측정해 **"모션마다 반경이 달라야 하나"에 아니오**로 답했다. 그 결과 구조가 갈렸고(개별 입력 X, GA 기본값 하나), 발차기 결함과 플레이어 캡슐 결함을 같이 고쳤다.

도중에 **SB 본편 Eve 콜리전 원본을 확보**해 그동안 쓰던 Scarlet 환산치를 폐기했다.

커밋 — Content `2a526b3` `[Combat]` / `6637d5a` `[BP]` (로컬)

---

## 1. 측정 목적과 결론

계획은 2026-08-14에 세워져 있었다. 찌르기/휘두르기를 갈라 각각 필요 반경을 내고, 크게 다르면 `ANS_MeleeTrace`에 개별 입력을 만든다는 것이었다.

**세 가지가 전부 "차등 불필요"를 가리켰다.**

| 검증 | 결과 |
|---|---|
| 찌르기/휘두르기 분리 | **찌르기 0개.** θ 중앙값 44~84도 |
| 날이 정면 중심선에 닿나 | **25개 창 전부 최소거리 0.0~0.6cm** |
| 스윕 빈틈 | **0 / 25.** 최악 39cm < 한계 74cm |

→ **GA 기본값 하나 + 예외 소수**로 확정. 노티 28개에 값을 박는 안은 폐기.

⚠️ **θ 측정에 구멍이 있다.** 루트모션을 제거한 좌표계에서 쟀는데 `02_Attack`은 전부 루트모션 클립이다. 찌르기가 몸이 파고들며 나가는 동작이면 그 전진량이 지워져 베기처럼 보인다. 작성자가 "찌르기는 확실히 있다"고 지적했고 **몽타주 목록을 받아 월드 기준으로 재측정하기로 했다. 미실행.**

## 2. 측정 방법 (재사용)

### 판정이 읽는 것부터 확인

```cpp
// AT_MeleeTrace.cpp:60~61 — 무기 메시의 소켓 월드 위치
const FVector CurStart = WeaponMesh->GetSocketLocation(StartSocket);
const FVector CurEnd   = WeaponMesh->GetSocketLocation(EndSocket);
```

GA 5개 CDO 실측 = `Weapon` 소스 / `Sword_Bottom` → `Sword_Tip` / `Sweep` / 반경 3.0.

**메모리에 적혀 있던 "검 축 = `sword_weapon_r` 본의 Z축"은 틀렸다.** 축은 무기 메시 소켓이 정하고, 그 무기는 `Sword_Weapon_RSocket`(`hand_r` 기준 회전 16.08 / 85.33 / 128.11)에 붙는다. 검 축 = **그 소켓 프레임의 −Y**.

곁가지 — `WeaponComponent.cpp:63`이 `GripPoint` 소켓이 있으면 역보정을 거는데 **검 메시에 그 소켓이 없다.** 보정이 안 걸리므로 검 트랜스폼 = 손 소켓 그대로다.

### 좌표계 확립 + 검산

프레임 포즈는 `AL.get_bone_pose_for_time()`이 **부모 상대(로컬)** 로 준다. `find_bone_path_to_root`로 체인을 얻어 컴포넌트 공간으로 합성해야 한다.

Idle 포즈로 검산했다.

```
pelvis  z  93.9      골반
head    z 160.5      머리
foot_l  z   8.2      발목
hand_r  x −24.1      오른손이 −X
```

→ **오른쪽 = −X / 정면 = +Y / 발 z 0.** 루트 이동이 +Y로 175cm 나온 것, 메시가 −90도 요로 붙는 것과 3중으로 일치.

### 몽타주↔시퀀스 매핑

몽타주는 `slot_anim_tracks`가 protected라 못 읽는다. **패키지 의존성에서 `AS_` 를 찾는 방식**으로 우회했다. 길이를 24개 전수 대조해 **소수점 4자리까지 동일** = 시각 1:1 확인.

⚠️ 몽타주 `get_num_frames`가 시퀀스보다 1 작게 나온다(99 vs 100). 프레임 인덱스 말고 **시각으로 다뤄야** 안전하다.

⚠️ **포즈 샘플링은 원본 `AS_` 시퀀스에만.** 몽타주에 하면 에디터가 죽는다.

## 4. 적용

### GA 5개 — 반경 3.0 → 20.0

`CapsuleRadiusOverride = 0`이 "GA 값 사용"이라 **GA 기본값만 바꾸면 28개 창에 자동으로 먹는다.** 노티마다 박으면 값 바꿀 때 28군데를 다시 돌아야 한다.

반경 20의 근거는 §5.

| | 이전 | 지금 |
|---|---|---|
| 검 판정 덩어리 | 129 × 6cm | **129 × 40cm** |
| 검 유효 거리 (칼축→적) | 37cm | **54cm** |
| 서브스텝 통과 한계 | 74cm | **108cm** (측정 최악 39cm) |

⚠️ **코드 기본값은 `TipLine` / 3.0인데 BP 5개가 `Sweep` / 3.0으로 덮고 있었다.** 모드는 BP가 진실. 반경은 코드값과 같아 델타 직렬화상 BP에 저장돼 있지 않았을 것으로 보이나 **확인 안 했다** — 이번엔 BP 쪽을 직접 고쳤다.

### 🔴 발차기 3개 — 축이 0이었다

`Combo_03_01` f8-15 · `04_02` f19-24 · `04_03` f23-32의 소켓 오버라이드가 **`foot_x → foot_x`, 같은 소켓**이었다.

```
Axis = 같은 점 − 같은 점 = 길이 0
HalfH1 = max(0 × 0.5, CapsuleRadius) = CapsuleRadius     // AT_MeleeTrace.cpp:159
→ 반경 3 짜리 구 하나 = 지름 6cm
```

발은 발목→발볼이 16.8cm다. **판정이 발의 3분의 1도 안 됐다.**

→ **`calf_x → ball_x` (51.8cm)** 로 교체. SB 근거는 §5. 반경 20이 얹혀 51.8 × 40cm 캡슐이 된다.

### `Combo_05_01` TipLine 해제

```cpp
// AT_MeleeTrace.cpp:124 — TipLine 은 LineTrace 다. CapsuleRadius 를 안 쓴다
bAnyHit = World->LineTraceMultiByObjectType(Hits, PrevEnd, CurEnd, ObjectParams, Params);
```

찌르기라고 판단해 넣은 것으로 보이나 **굵기 0인 선**이 된다. 찌를수록 두께가 필요한데 정반대였다. 해제해서 다른 24개와 같은 굵기를 쓴다.

**최종 = 28개 중 예외 3개(발차기)만 남고 전부 GA 상속.**

## 5. ★ SB 본편 Eve 콜리전 원본 확보

### "덤프에 없다"는 결론이 아니라 추출 상태였다

2026-08-14까지 두 세션 동안 **"본편 Eve 콜리전은 덤프에 없다"** 고 기록하고 Scarlet(홍련) 보스 수치를 몸 크기로 환산해 쓰고 있었다.

**`Art/Character` 폴더가 추출이 안 돼 있었을 뿐이다.** 작성자가 다시 받으니 콜리전 파일 **83개**(공격 그룹 있는 것 68개)와 `CH_P_EVE_01_Collision.json`이 그대로 있었다.

내 조회도 부실했다 — `ls ... 2>/dev/null`을 써서 **"비었다"와 "경로가 틀렸다"를 구분 못 한 채** 없다고 단정했다.

### Eve 실측

```
Collision_Weapon              Trace  Thickness 30   weapon_bottom -> weapon_top   bDefaultActive: TRUE
Collision_WeaponAndRight/LeftArm     Thickness 30   + 팔 축
Collision_WeaponAndBody       Trace  Thickness 50   + EveSpine Box
Collision_WeaponBig           Box    100 x 40 x 40
Collision_WeaponHeavy         Box    150 x 60 x 60
Collision_RightFoot           Box    EveRightCalfLong 15x70x15  on Bip001-R-Calf  relLoc Y −70
발 실제 EveRightFoot          Box    5x10x5  on Foot    ← 발차기 그룹이 안 쓴다
Eve 캡슐   이동 R40 / 피격 R50 / HalfHeight 95
```

**밝힌 것 셋**

1. **큰 공격은 두께를 키우는 게 아니라 형상을 Box로 갈아탄다.** 기본·팔·몸통만 소켓 축 트레이스(우리 `Sweep`과 동형)고 Big·Heavy·발차기는 Box다. 우리에겐 Box 모드가 없다
2. **Eve의 기본 무기 판정은 상시 켜져 있다**(`bDefaultActive: true`). 스킬이 더 큰 그룹으로 갈아끼운다. 우리는 노티 구간에만 도는 반대 모델
3. **발차기는 Calf에 붙고 중심이 정강이에서 70cm 아래다** — 발을 한참 지나쳐 뻗는다. 우리 `calf → ball`(51.8cm) 결정의 직접 근거이나, **SB보다는 여전히 짧다**

### 반경 20의 근거

```
Eve Thickness 30 을 지름으로 읽으면    반경 15 × 0.85 = 12.75
Eve Thickness 30 을 반지름으로 읽으면  반경 30 × 0.85 = 25.5
                                       (0.85 = 우리 R34 / Eve 이동캡슐 R40)
```

**어느 읽기로든 20이 밴드 안**이라 지금은 가릴 필요가 없다.

⚠️ **미확정 2개** — `Thickness`가 반지름이냐 지름이냐 / `BoxExtent`가 half냐 full이냐. 후자는 `EveHead`·`EveRightFoot`은 half로, `EveRightCalf`는 full로 읽어야 실물 크기가 나온다. **치수를 그대로 베끼지 말고 비율·구조만 가져올 것.**

## 6. SB 캐릭터 대조 — 가설이 깨졌다

"Eve 피격 캡슐 R50 vs 우리 R34니까 우리가 맞추기 어렵다"고 쓸 뻔했는데 **실제 melee 피격은 캡슐이 아니었다.**

```
AttackedCollisionGroupArray "Default" (bDefaultActive: true)
= EveHead / EveSpine / R·L Thigh / R·L Calf / R·L Foot   Box 8개
팔은 없다 (팔 형상은 PhotoMode 전용)
EveSpine = 12 × 35 × 12
```

**SB는 부위별 박스로 맞는다.** 몸통이 half로 읽어도 폭 24cm — **우리 캡슐 R34(지름 68cm)보다 좁다.**

→ **우리 적이 SB보다 맞추기 쉽다.** 부위별로 쪼개면 오히려 빡빡해진다. **피격/이동 분리는 안 한다.**

곁가지 — 사자형 몬스터(`CH_M_NA_02`)는 이동 R50 / 피격 R20 + 손발 부위별로 Eve와 반대다. 캐릭터마다 다르다.

### 대조표

| 항목 | SB (Eve) | 우리 | 판단 |
|---|---|---|---|
| 이동 캡슐 | R40 H95 · Ch11 · **Pawn Ignore** | R34 H95 / 적 R34 H88 · `ECC_Pawn` · **Block** | 캐릭터끼리 밀친다 |
| melee 피격 | 부위별 Box 8개 | 이동 캡슐이 겸함 | **우리가 관대** — 유지 |
| **AirControl** | **0.7** | 0.05 | 🔴 고침 |

## 7. 🔴 플레이어 캡슐이 메시와 안 맞았다


### `AirControl`이 공중 콤보 중에는 안 먹는다

루트모션 몽타주가 도는 동안은 이동을 애니가 쥐고 있어 `CharacterMovement`의 공중 가속이 개입할 자리가 없다. **적용 범위 = 몽타주 밖 공중 구간**(점프·낙하·콤보 사이).

공중 콤보 도중에도 틀려면 모션 워핑이나 루트모션 스케일 쪽이라 별개 작업이다.
