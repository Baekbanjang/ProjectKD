## 4. ★★ 타격 판정 — 우리가 직접 베낄 구간

### 4-1. 두 방식과 사용 구분 (03:54 · 04:06 슬라이드)
```
Triangle-Hitbox Intersection
  Socket들의 이전 프레임 위치와 현재 프레임 위치를 Triangle로 구축하여 판정
  용도 = 검처럼 얇은 무기 · 정확한 공격 검출이 필요할 때

Hitbox Sweep Trace
  ShapeComponent의 이전 프레임 위치로부터 현재 프레임 위치를 Sweep Trace하여 판정
  용도 = 몸통 박치기 · 느리고 큰 무기 · 영역 판정
  ⚠️ 소켓 기반 Triangle 방식보다 정확도가 낮다
```

**트라이앵글 구성** (04:12 다이어그램)
```
5Frame 소켓 2점 (칼끝 · 칼자루)  +  6Frame 소켓 2점
   → 사각형을 만들고 대각선을 그어 삼각형 2개
   → 이 삼각형과 히트박스의 교차로 판정
```

🔴 **우리는 캡슐 스윕(`Hitbox Sweep Trace`) 쪽이다.** SB 기준으로 정확도가 낮은 방식이며,
용도상 "느리고 큰 무기"용인데 우리는 검에 쓰고 있다.

### 4-2. 정확도가 떨어지는 두 경우
```
① 공격이 빠른 경우      궤적이 직선으로 끊김
② FPS가 낮은 경우       궤적 중간이 통째로 누락
```

### 4-3. 해결 = Transform 보간 (05:00 슬라이드)
```
UAnimSequence 의 RawAnimationData 를 이용
Socket 의 Parent Bone Transform 을 보간하여,
이전 프레임과 현재 프레임 사이의 Bone Transform 계산
```
결과 = 30FPS에서도 60FPS와 동등하게 촘촘한 궤적 샘플이 나온다(05:24 좌우 비교).

### 4-4. 경사면 문제와 LookAt IK, 그리고 그 함정
```
문제   경사 위 몬스터를 공격하면 궤적이 발 아래로 생성되어 타격 실패
해결   LookAt IK AnimNode — 상체 본이 몬스터 중점을 바라보도록 회전

★ 함정 — 고쳤더니 원래 문제가 되살아난다
  IK 회전 후의 실제 본 위치 ≠ RawAnimationData 에 저장된 본 위치
  → 궤적 어긋남 재발

2차 보정 (06:24 슬라이드)
  RawAnimationData에 저장된 Transform과 Animation된 Bone의 Transform 차이를 구함
  구해진 Transform을 위치 보간 처리에 적용
```

### 4-5. 트레일도 같은 병을 앓았다
```
문제   AnimTrailEmitter 가 현재 프레임 위치 기반이라 검 궤적이 부드럽지 않음
해결   FParticleAnimTrailEmitterInstance::Spawn 함수에서 보간된 경로를 추가로 생성
```

## 6. 프레임 분산 처리 (11:47)

```
Frame Hitching
  1Frame에 많은 처리를 할 경우, Hitching이 발생
  1Frame에 반드시 실행하지 않아도 되는 항목은 여러 Frame에 나눠서 실행
  Show Particle, Projectile 등

Show Particle Frame 분산
  분산 처리 가능한 객체를 선별
  1Frame에 1ms의 시간 제한
  생성 후, 처음 Tick DeltaTime은 지연된 시간을 포함     ← 시뮬레이션 시간 보정

Projectile Frame 분산
  1Frame에 6개의 생성 제한
  최대 생성 지연 시간은 Shot Time 이하로 설정
```

**실측** — 파티클 한 프레임 25ms → 분산 후 평균 15ms
**발사체** — 보스 **엘더**가 한 프레임에 20개+ 생성
```
FSBProjectileManager::Spawn
  최적화 전  Inclusive 7.7 ms  / % of Parent 82.95% / % of Root 30.25%
  최적화 후  Inclusive 1.9 ms  / % of Parent 53.57% / % of Root 9.6%
```

## 7. PhysScene Update (13:29)

```
End Physics Tick에서 PhysXTask의 처리 시간으로 인해, GameThread의 대기 시간이 발생
PhysScene에 등록된 Rigid Dynamic 처리 부하
```
원인 = **65본 몬스터 10마리 → Rigid Dynamic 650개 등록**
몬스터 실측 = `65 Bones, 55 Considered for bounds (100%), 61 Constraints`, `CollisionBody: 11`

### 해결 (14:39) — 엔진 코드 개조
```
SkeletalMeshComponent의 BodyInstance는 Mesh의 Collision 설정을 따라감
UBodySetup에 bNotRigidDynamic 변수 추가
bNotRigidDynamic가 True인 경우, NoCollision으로 CollisionEnableType 설정
```
```cpp
ECollisionEnabled::Type
FBodyInstance::GetCollisionEnabled_CheckOwner() const
{
    ...
    else if (const USkeletalMeshComponent* SkelMeshComp = Cast<USkeletalMeshComponent>(OwnerComponentInst))
    {
        if (bNotRigidDynamic)
        {
            return ECollisionEnabled::NoCollision;
        }
        return SkelMeshComp->BodyInstance.CollisionEnabled;
    }
    ...
}
```

**결과** `Wait Time 3.9 ms → 0 ms` / `FPhysXTask 4 ms → 1 ms`

⚠️ **부작용** — 물리 등록에서 뺀 본은 **충돌도 사라진다**(몬스터가 드럼통을 그대로 관통).
→ 물리 충돌용 **Capsule Component 별도 추가**로 메움. 정확하진 않지만 충돌은 발생.

## 9. CharacterMovement 병렬화 (17:09~25:24, 발표자 이동익)

**착수 조건** = 몬스터 20여 마리 구간에서 무브먼트 틱 **2.8ms** 실측.

### 9-1. 로직 4분류 (19:00 슬라이드 원문)
```
Move
  병렬 수행 대상 / 게임의 이동과 관련된 로직
  대부분의 로직이 스레드 세이프 / 그렇지 않은 로직은 '지연' 처리 필요

Overlap
  병렬 수행 불가
  위치 갱신 시 컴포넌트 오버랩 이벤트 갱신
  스레드 세이프 하지 않을 가능성 높음 — 블루프린트 함수 호출 때문

Physics
  병렬 수행 가능, 하지만 제외
  위치 갱신 시 물리 오브젝트 갱신 / 스레드 세이프
  PhysX Lock 으로 인한 스레드 대기 발생
  (물리 오브젝트 갱신으로 인한 WriteLock, 여러 스레드에서 ReadLock 대기)

Deferred Move
  '지연' 처리 된 Move 로직
  병렬 수행 완료 후 게임 스레드에서 실행
  블루프린트 호출, 다른 액터 참조 등
```

### 9-2. 구현 3가지 (21:06 슬라이드 원문)
```
무브먼트 매니저 클래스 구현
  무브먼트 Tick 의 병렬 수행을 매니저 클래스에서 실행
  병렬 수행 후 Deferred Move 등 후속 작업 담당
  무브먼트 컴포넌트가 매니저에 등록 & 해제 되도록 함수 오버라이드 필요

IsInGameThread() 타 스레드 접근 허용
  게임 스레드용 함수를 다른 스레드에서 접근 가능하도록 처리 필요
  병렬 수행 완료 후, 게임 스레드용 함수로 전환

스레드 세이프하지 않은 로직 분리
  Deferred Move, Overlap, Physics 의 '지연' 처리
  블루프린트 함수 또는 델리게이트 호출, 다른 액터 & 컴포넌트 참조,
  애니메이션·사운드 등의 에셋 로드·사용 로직 등
```

### 9-4. Overlap/Physics 지연 = FScopedMovementUpdate 활용 (23:30)
```
FScopedMovementUpdate 객체 활용
SceneComponent 가 해당 객체 소유 시, 위치 정보가 갱신되어도 Overlap, Physics 갱신 수행하지 않음
병렬 수행 전, 컴포넌트에 객체 할당
병렬 수행 후, 할당 된 객체 제거하여 갱신
```
```
// 의사코드
for each MovementComponent in ParallelComponents
    MovementComponent->DeferredUpdater = new FScopedMovementUpdate(MovementComponent, ~);

SetParallelForInGameThread(true);      // IsInGameThread() 타 스레드 접근 허용
ProcessMovementParallelTick();         // 병렬 수행
SetParallelForInGameThread(false);     // 접근 [?]

for each MovementComponent in ParallelComponents   // Deferred Move 수행, Overlap·Physics 갱신
    MovementComponent->ProcessDeferredMove();
    delete MovementComponent->DeferredUpdater;
```
★ 원래 `FScopedMovementUpdate`는 무브먼트 틱 중 빈번한 갱신을 막는 엔진 기본 기능인데,
그 범위를 **"병렬 수행 완료까지"로 늘려** 지연 처리에 전용했다.

⚠️ 무브먼트 매니저의 **구체적 C++ 클래스명은 슬라이드에 없다.** 다만 프로파일러에
`FSBCharacterMovementUpdateManagerTickFunction::Tick(TG_PrePhysics)` / `::ExecuteTick` 이 찍혀 있다.

## 10. 실시간 절단 (25:30)

### 10-1. 방식 비교
```
전통적인 방법 — 모델링 교체 방식
  미리 절단 된 메쉬, 애니메이션 리소스 준비 / 절단 시점에 모델링을 교체
  절단 부위가 다양해 질수록 리소스 작업량 증가

실시간 절단 방식
  추가 모델링 작업 없이 범용적으로 사용하기 위함
  절단 메시와 래그돌 상태의 스켈레탈 메시의 자연스러운 표현
  안정적인 성능
```

### 10-2. 단점과 대응 (26:55)
```
실시간 절단, 버텍스 스키닝 성능 비용 발생
  → 절단 메시 정보 캐싱, 다른 스레드에서 스키닝 업데이트 등 최적화 진행
절단 실패 가능성 (절단 면이 생성되지 않음, 절단 메시 형상이 비정상적)
  → 매끄럽게 절단되는 부위와 한계 각도를 선정하여 화이트 리스트로 관리
```

### 10-3. 초기 아이디어의 한계 (27:28)
```
SliceProceduralMesh 이용한 절단 메시 생성 방식 — 언리얼 기본 함수
  스켈레탈 메시를 본뜬 프로시저럴 메시 생성하여 절단
    모든 버텍스를 본뜨기 때문에 메시 생성 비용 증가
  래그돌을 이용한 사망 연출 불가능
    절단 당시 모습 유지 / 원하지 않는 부위까지 절단
```

### 10-4. 개선 3가지 (28:17)
```
절단 부위 최소화     프로시저럴 메시 생성 비용 감소 / SliceProceduralMesh 사용 가능 / 원하는 부위만 절단
스켈레탈 + 프로시저럴 혼용   래그돌 + 절단 면 모두 표현 가능
버텍스 스키닝        절단 메시가 래그돌의 움직임에 대응 / 자연스러운 움직임 표현
```

### 10-5. ★ 절단 프로세스 (29:11 슬라이드 원문)
```
생성된 프로시저럴 메시를 SliceProceduralMesh 로 절단
  절단 된 메시는 각각 절단 본과 부모 본에 어태치
BreakConstraint 함수로 본을 끊고, AddImpulse 함수로 절단 본을 날려 절단 상태 표현
스켈레탈 메시의 본 트랜스폼 정보로 프로시저럴 메시 스키닝
  래그돌 상태를 프로시저럴 메시에 반영
```

### 10-6. 이격과 스키닝
```
이격    스켈레탈 메시와 프로시저럴 메시의 경계에 이격 발생
해결    절단 부위 생성 시, 본 경계와 가까운 버텍스들을 추가로 수집
        (스킨 웨이트 가진 버텍스 + 본 경계에 위치한 버텍스)

버텍스 스키닝
  프로시저럴 메시는 절단 당시 모습 유지 / 스켈레탈 메시는 래그돌 상태
  본 트랜스폼 정보로 프로시저럴 메시를 스키닝
    - 절단면은 스킨 웨이트 정보가 없기 때문에 제외
  절단면에서 멀어질수록 스키닝 웨이트를 늘려간다
```

### 10-7. 절단 최적화 (31:12)
```
절단 메시 데이터 캐싱
  절단 대상 본의 섹션, 트라이앵글 인덱스 정보 등을 셋에 기록
  트라이앵글 인덱스로 스켈레탈 메시의 버텍스 조회하여 프로시저럴 메시 생성
  프로시저럴 메시 = 스켈레탈 메시의 절단 부위 — 섹션, 버텍스, 메테리얼 등 모두 동일

  캐시 데이터 실측:
    Bone Name: Bip001-Spine / Base Index: 0 / Num Triangles: 1258
    Start Triangle Index: 8907 / Triangle Count: 2 / Vertex Type: ChildSkinned

버텍스 스키닝 (Other Thread)
  절단 메시 스키닝 매니저 생성하여 활용
  다른 스레드에 상주하여 절단 메시 스키닝 요청을 받으면 활동
  프로시저럴 메시의 버텍스 갱신이기 때문에 스레드 세이프
  실질적 절단 비용은 프로시저럴 메시 생성 뿐

  Game Thread   Character Tick → Slice Mesh Update  ──Push Job──┐
  Other Thread   Slice Mesh Skinning Manager ← Skinning 1 → 2 → Wait
```

## 12. ★ 우리 프로젝트 대조 — 무엇이 맞았고 무엇이 다른가

### 12-1. 이미 맞게 가고 있는 것
| 항목 | SB | 우리 | 판정 |
|---|---|---|---|
| 히트스톱 시간 | **0.07초** (60fps 4~5프레임) | `AttackerHitStopDuration 0.08` | ✅ 거의 동일 |
| 히트스톱 대상 | 공격자만 | `KDHitStopComponent` = 공격자 | ✅ 동일 |
| 히트스톱 / 전역 시간 = 2층 | 별개 시스템 | `KDHitStopComponent` + `UKDSlowMotionSubsystem` | ✅ 동일 구조 |

| 판정 = 노티 기반 | ShowMaker 스텝 | `ANS_MeleeTrace` | ✅ 같은 발상 |

### 12-2. ★ 어제 결론 정정
어제 Show 데이터 조사에서 **"SB는 일반 타격에 히트스톱이 없다"**고 했는데 **틀렸다.**
```
히트스톱 (애니메이션 정지)   0.07초, 공격자만       ← 코드에 있다. Show 데이터엔 없음
TimeScale (전역 시간 배율)   0.2배 0.15초, 반격만    ← Show 데이터에 있다
```
두 개가 **별개 시스템**이라 Show 데이터를 뒤져도 평타 히트스톱이 안 나왔던 것이다.
(그때 "Show 데이터 범위 안에서만 참"이라 단서를 단 것은 유효했다)
